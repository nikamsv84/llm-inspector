# 📓 دفترچه یادداشت توسعه (Mini Burp Suite)

این فایل شامل یادداشت‌های شخصی، دلایل تصمیمات معماری و چالش‌های فنی پروژه به زبان فارسی است.

---

## 💡 چرا حتی در پروژه کوچک به Connection Pool نیاز داریم؟

توی نگاه اول ممکنه فکر کنیم چون پروژه‌مون شخصیه و کلاینت‌های زیادی نداره، ساختن یک کانکشن ساده کافیه. اما در عمل:

1. **تداخل سرور سوکت و FastAPI:** 
   * **Socket Inspector** به محض گرفتن پکت، کوئری `INSERT` می‌زنه.
   * **FastAPI Dashboard** هم‌زمان برای بروزرسانی مانیتور، کوئری `SELECT` می‌زنه.
   اگر از یک کانکشن مشترک استفاده کنیم، دیتابیس قفل می‌کنه (`OperationalError`).

2. **سنگین بودن ساخت Process در PostgreSQL:**
   پستگرس برای هر کانکشن جدید یک پروسس مجزا در سیستم‌عامل می‌سازه. ساخت و بستن مداوم کانکشن باعث افت شدید سرعت (Latency) در پراکسی میشه.

*نتیجه:* با یک Pool کوچک (`min_size=2, max_size=5`) هم مشکل تداخل حل میشه هم سرعت بالا می‌مونه.

## 💡 ۱. اجرای خودکار Schema از روی فایل `.sql`

* **جداسازی کدهای SQL از پایتون:** به‌جای نوشتن کوئری‌های `CREATE TABLE` داخل کد پایتون، فایل‌های SQL به‌صورت مستقل نگهداری می‌شوند. این کار خوانایی کد را بالا برده و مدیریت تغییرات دیتابیس (Schema Migrations) را راحت‌تر می‌کند.
* **استفاده از مسیردهی پویا (Dynamic Pathing):** برای جلوگیری از خطای `FileNotFoundError` هنگام اجرای برنامه از دایرکتوری‌های مختلف (مثل Root پروژه یا زیرپوشه‌ها)، مسیر فایل SQL با استفاده از کتابخانه `pathlib` و نسبت به محل خودِ فایل `db_manager.py` ساخته می‌شود (`Path(__file__).parent`).
* **تثبیت تغییرات (`conn.commit()`):** در `psycopg3` اجرای دستورات ساخت جدول (DDL) تا زمانی که `commit` نشوند در دیتابیس اعمال نخواهند شد؛ لذا فراخوانی `conn.commit()` پس از اجرا الزامی است.

## 🏗️ ۲. یکپارچه‌سازی Database Manager

* **جلوگیری از کد تکراری (DRY):** به‌جای داشتن دو فایل مجزای `db_manager.py` (یکی در پوشه `dashboard` و یکی در `inspector_tools`)، یک ماژول واحد مدیریت دیتابیس طراحی می‌شود تا هر دو بخش (سرور سوکت و FastAPI) از یک منطق مشترک استفاده کنند.

## 🛡️ ۳. عدم استفاده از f-String در کوئری‌های SQL (جلوگیری از SQL Injection)

* **خطر SQL Injection:** در هنگام نوشتن دستورات `INSERT` یا `SELECT` به هیچ وجه از f-String پایتون برای جاگذاری متغیرها استفاده نمی‌کنیم. اگر ورودی کاربر یا داده‌های دریافت شده از شبکه شامل کاراکترهای مخرب (مثل `' OR 1=1 --`) باشند، ترکیب مستقیم متغیر در رشته کوئری باعث تغییر منطق SQL یا حتی پاک شدن داده‌ها می‌شود.
* **استفاده از Parameterized Queries (`%s`):** به‌جای f-String، مقادیر ورودی را در قالب پارامترهای جداگانه (به‌صورت Tuple) به متد `cur.execute()` پاس می‌دهیم:
  ```python
  # ❌ روش ناامن (هرگز استفاده نشود)
  cur.execute(f"INSERT INTO raw_requests (host) VALUES ('{packet.target_host}')")

  # ✅ روش امن و استاندارد
  cur.execute("INSERT INTO raw_requests (host) VALUES (%s)", (packet.target_host,))
</div>

## 🆔 ۴. دریافت اتوماتیک Primary Key با `RETURNING id`

* **جلوگیری از کوئری مجدد (Avoid Extra SELECT):** پس از ثبت یک رکورد جدید با دستور `INSERT`، سیستم برای مراحل بعدی (مثل اضافه کردن به صف Intercept) نیاز به شناسه (`id`) آن رکورد دارد. به‌جای اجرای یک کوئری مجدد `SELECT` برای پیدا کردن آخرین ID ثبت‌شده، از قابلیت native پستگرس یعنی `RETURNING id` در همان کوئری `INSERT` استفاده می‌کنیم.
* **جلوگیری از Race Condition:** در برنامه‌های هم‌زمان (Concurrent)، اجرای `SELECT MAX(id)` ممکن است ID اشتباهی (متعلق به یک Thread دیگر) را برگرداند. عبارت `RETURNING id` تضمین می‌کند دقیقاً شناسه همان سطری که توسط Thread جاری ثبت شده برگردانده شود.
* **کاهش Latency شبکه:** ترکیب اینسرت و دریافت آی‌دی در یک Round-trip شبکه، تاخیر (Latency) برنامه را به حداقل می‌رساند.

## 🗄️ ۵. نگاشت هدرهای HTTP به‌صورت JSON/JSONB

* **انعطاف‌پذیری ساختار داده (Schema Flexibility):** هدرهای HTTP ساختار متغیری دارند (تعداد و نام کلیدها در هر درخواست متفاوت است). به‌جای ساخت ستون‌های متعدد یا جداول رابطه‌ای پیچیده، تمام هدرها به‌صورت یک دیکشنری پایتون دریافت شده و با تابع `json.dumps()` به فرمت استاندارد JSON تبدیل و در یک ستون ذخیره می‌شوند.
* **حفظ امکان Query زدن:** دیتابیس PostgreSQL از نوع داده JSON/JSONB پشتیبانی کامل می‌کند؛ بنابراین با وجود ذخیره‌سازی به‌صورت JSON، همچنان می‌توان روی هدرهای خاص (مثل `User-Agent` یا `Authorization`) کوئری‌های سریع زد.

---

## 🔒 ۶. مدیریت چرخه حیات (Lifecycle) استخر اتصالات

* **باز و بستن صریح (Explicit Pool Lifecycle):** برای جلوگیری از باز ماندن اتصالات معلق (Dangling Connections) یا مصرف بی‌رویه RAM در PostgreSQL، مدیریت استخر اتصال به توابع صریح `open_pool()` و `close_pool()` سپرده شد.
* **استفاده از ساختار `try ... finally`:** فراخوانی `close_pool()` در بلوک `finally` تضمین می‌کند که حتی در صورت بروز Exception یا Crashing برنامه، تمامی کانکشن‌های استخر به‌صورت کاملاً ایمن و منظم بسته می‌شوند.

## 🚦 ۷. متوقف‌سازی و آزادسازی نخ‌ها با `threading.Event` (مکانیزم Intercept)

* **چالش توقف بی‌ضرر (Non-busy Waiting):** در ابزارهای Intercept مانند Burp Suite، هنگامی که پکت شبکه دریافت می‌شود، اجرای نخ (Thread) سوکت کلاینت باید تا زمان تعیین تکلیف توسط کاربر (Forward یا Drop) متوقف بماند. استفاده از حلقه‌های شرطی مداوم (مثل `while True`) باعث درگیر شدن ۱۰۰ درصدی CPU (High CPU Usage) می‌شود.
* **استفاده از `threading.Event` و `event.wait()`:** با پیاده‌سازی مکانیزم ایونت در پایتون، نخ سوکت کلاینت بدون مصرف هیچ‌گونه منابع پردازشی CPU به حالت **Sleep / Block** می‌رود. به محض فراخوانی دستور `event.set()` توسط API دشبورد (پس از کلیک کاربر)، نخ جاری بلافاصله از حالت بلاک خارج شده و ادامه مسیر (ارسال یا قطع ارتباط) را طی می‌کند.
* **ایمنی در دسترسی هم‌زمان (Thread-Safety با Mutex):** از آنجا که چندین نخ کلاینت به‌صورت هم‌زمان ایونت‌های خود را در دیکشنری مشترک `intercept_events` ثبت یا حذف می‌کنند و API دشبورد نیز در نخی مجزا به آن دسترسی دارد، تمام عملیات‌های خواندن/نوشتن روی این دیکشنری تحت یک قفل متقابل (`threading.Lock()`) انجام می‌شود تا از وقوع **Race Condition** و خطاهای خطرساز تداخل حافظه جلوگیری گردد.
* **مدیریت زمان انقضا (Timeout Handling) و پاک‌سازی حافظه:**
  * تعیین مقدار تایم‌اوت (`timeout=300.0`) در `event.wait()` تضمین می‌کند در صورت عدم واکنش کاربر پس از ۵ دقیقه، نخ کلاینت برای همیشه معلق نمانده و به‌صورت پیش‌فرض (Fallback) پکت را Forward کند.
  * قرار دادن متد `pop` در بلوک `finally` تضمین می‌کند ایونت‌ها پس از تعیین تکلیف حتماً از حافظه RAM پاک شوند تا سیستم دچار **Memory Leak** نشود.

## 🔄 ۸. ارتباط بین‌پروسسی (IPC) و همگام‌سازی state از طریق Database Polling

* **چالش تداخل پروسس‌ها (Process Memory Boundary):** سرور پروکسی (`inspector_server.py`) و API دشبورد (`FastAPI`) در دو پروسس کاملاً مجزا با فضای حافظه (RAM) مستقل اجرا می‌شوند. بنابراین، اشیائی مانند `threading.Event()` که در RAM سرور ساخته می‌شوند، از داخل پروسس دشبورد قابل دسترسی نیستند و فراخوانی متد `.set()` روی آن‌ها کارساز نخواهد بود.
* **راهکار Database-backed Polling:** برای عبور از مرز حافظه پروسس‌ها، **پستگرس به عنوان رسانهٔ مشترک ارتباطی (IPC Channel)** انتخاب شد. تابع `wait_for_user_action` طوری بازنویسی شد که هر ۵۰۰ میلی‌ثانیه وضعیت ستون `status` را از جدول `intercept_queue` استعلام (Poll) کند.
* **دستاورد:** با این ساختار، هر برنامه‌ای (چه اسکریپت‌های تست، چه API دشبورد و چه ابزارهای CLI خارجی) می‌تواند با یک `UPDATE` ساده روی دیتابیس، وضعیت پکت را تغییر دهد و سرور پروکسی آنی از حالت Block خارج می‌شود.

---

## 🛑 ۹. پیاده‌سازی منطق Drop و قطع ارتباط امن کلاینت

* **عدم ارسال به مقصد (Interception Enforcement):** در صورتی که اکشن دریافتی برای یک `request_id` برابر با `dropped` باشد، سرور پروکسی موظف است پردازش را متوقف کرده و به هیچ عنوان اتصال سوکت سمت مقصد (`httpbin` یا هر تارگت دیگری) را برقرار نکند.
* **پاسخ بلاک صریح (403 Forbidden):** به‌جای رها کردن ناگهانی سوکت کلاینت (که باعث خطای `ECONNRESET` و گیج شدن کلاینت می‌شود)، یک پاسخ استاندارد `HTTP/1.1 403 Forbidden` همراه با بدنهٔ توضیحی برای کلاینت ارسال شده و سپس سوکت به‌صورت کاملاً پاکیزه بسته می‌شود.
* **تضمین عدم ایجاد Deadlock و Leaked Thread:** با بسته شدن سوکت کلاینت در بلوک `dropped` و اجرای قطعه‌کد پاک‌سازی در `finally`، تمام منابع تخصیص‌یافته به آن ترید (شامل اتصال دیتابیس و آی‌دی ایونت در حافظه) آزاد می‌شوند.
