# 📓 دفترچه یادداشت توسعه (Mini Burp Suite)

این فایل شامل یادداشت‌های شخصی، دلایل تصمیمات معماری و چالش‌های فنی پروژه به زبان فارسی است.

---

## 💡 چرا حتی در پروژه کوچک به Connection Pool نیاز داریم؟

توی نگاه اول ممکنه فکر کنیم چون پروژه‌مون شخصیه و کلاینت‌های زیادی نداره، ساختن یک کانکشن ساده کافیه. اما در عمل:

1. **تداخل سرور سوکت و FastAPI:** 
   * **Socket Inspector** به محض گرفتن پکت، کوئری `INSERT` می‌زنه.
   * **FastAPI Dashboard** هم‌زمان برای بروزرسانی مانیتور، کوئری `SELECT` می‌زنه.
   اگر از یک کانکشن مشترک استفاده کنیم، دیتابیس قفل می‌کنه (`OperationalError`).

2. **سنگین بودن ساخت Process در PostgreSQL:**
   پستگرس برای هر کانکشن جدید یک پروسس مجزا در سیستم‌عامل می‌سازه. ساخت و بستن مداوم کانکشن باعث افت شدید سرعت (Latency) در پراکسی میشه.

*نتیجه:* با یک Pool کوچک (`min_size=2, max_size=5`) هم مشکل تداخل حل میشه هم سرعت بالا می‌مونه.

## 💡 ۱. اجرای خودکار Schema از روی فایل `.sql`

* **جداسازی کدهای SQL از پایتون:** به‌جای نوشتن کوئری‌های `CREATE TABLE` داخل کد پایتون، فایل‌های SQL به‌صورت مستقل نگهداری می‌شوند. این کار خوانایی کد را بالا برده و مدیریت تغییرات دیتابیس (Schema Migrations) را راحت‌تر می‌کند.
* **استفاده از مسیردهی پویا (Dynamic Pathing):** برای جلوگیری از خطای `FileNotFoundError` هنگام اجرای برنامه از دایرکتوری‌های مختلف (مثل Root پروژه یا زیرپوشه‌ها)، مسیر فایل SQL با استفاده از کتابخانه `pathlib` و نسبت به محل خودِ فایل `db_manager.py` ساخته می‌شود (`Path(__file__).parent`).
* **تثبیت تغییرات (`conn.commit()`):** در `psycopg3` اجرای دستورات ساخت جدول (DDL) تا زمانی که `commit` نشوند در دیتابیس اعمال نخواهند شد؛ لذا فراخوانی `conn.commit()` پس از اجرا الزامی است.

## 🏗️ ۲. یکپارچه‌سازی Database Manager

## 🛡️ ۳. عدم استفاده از f-String در کوئری‌های SQL (جلوگیری از SQL Injection)

* **خطر SQL Injection:** در هنگام نوشتن دستورات `INSERT` یا `SELECT` به هیچ وجه از f-String پایتون برای جاگذاری متغیرها استفاده نمی‌کنیم. اگر ورودی کاربر یا داده‌های دریافت شده از شبکه شامل کاراکترهای مخرب (مثل `' OR 1=1 --`) باشند، ترکیب مستقیم متغیر در رشته کوئری باعث تغییر منطق SQL یا حتی پاک شدن داده‌ها می‌شود.
* **استفاده از Parameterized Queries (`%s`):** به‌جای f-String، مقادیر ورودی را در قالب پارامترهای جداگانه (به‌صورت Tuple) به متد `cur.execute()` پاس می‌دهیم:
  ```python
  # ❌ روش ناامن (هرگز استفاده نشود)
  cur.execute(f"INSERT INTO raw_requests (host) VALUES ('{packet.target_host}')")

  # ✅ روش امن و استاندارد
  cur.execute("INSERT INTO raw_requests (host) VALUES (%s)", (packet.target_host,))
</div>

## 🆔 ۴. دریافت اتوماتیک Primary Key با `RETURNING id`

* **جلوگیری از کوئری مجدد (Avoid Extra SELECT):** پس از ثبت یک رکورد جدید با دستور `INSERT`، سیستم برای مراحل بعدی (مثل اضافه کردن به صف Intercept) نیاز به شناسه (`id`) آن رکورد دارد. به‌جای اجرای یک کوئری مجدد `SELECT` برای پیدا کردن آخرین ID ثبت‌شده، از قابلیت native پستگرس یعنی `RETURNING id` در همان کوئری `INSERT` استفاده می‌کنیم.
* **جلوگیری از Race Condition:** در برنامه‌های هم‌زمان (Concurrent)، اجرای `SELECT MAX(id)` ممکن است ID اشتباهی (متعلق به یک Thread دیگر) را برگرداند. عبارت `RETURNING id` تضمین می‌کند دقیقاً شناسه همان سطری که توسط Thread جاری ثبت شده برگردانده شود.
* **کاهش Latency شبکه:** ترکیب اینسرت و دریافت آی‌دی در یک Round-trip شبکه، تاخیر (Latency) برنامه را به حداقل می‌رساند.

---

## 🗄️ ۵. نگاشت هدرهای HTTP به‌صورت JSON/JSONB

* **انعطاف‌پذیری ساختار داده (Schema Flexibility):** هدرهای HTTP ساختار متغیری دارند (تعداد و نام کلیدها در هر درخواست متفاوت است). به‌جای ساخت ستون‌های متعدد یا جداول رابطه‌ای پیچیده، تمام هدرها به‌صورت یک دیکشنری پایتون دریافت شده و با تابع `json.dumps()` به فرمت استاندارد JSON تبدیل و در یک ستون ذخیره می‌شوند.
* **حفظ امکان Query زدن:** دیتابیس PostgreSQL از نوع داده JSON/JSONB پشتیبانی کامل می‌کند؛ بنابراین با وجود ذخیره‌سازی به‌صورت JSON، همچنان می‌توان روی هدرهای خاص (مثل `User-Agent` یا `Authorization`) کوئری‌های سریع زد.

---

## 🔒 ۶. مدیریت چرخه حیات (Lifecycle) استخر اتصالات

* **باز و بستن صریح (Explicit Pool Lifecycle):** برای جلوگیری از باز ماندن اتصالات معلق (Dangling Connections) یا مصرف بی‌رویه RAM در PostgreSQL، مدیریت استخر اتصال به توابع صریح `open_pool()` و `close_pool()` سپرده شد.
* **استفاده از ساختار `try ... finally`:** فراخوانی `close_pool()` در بلوک `finally` تضمین می‌کند که حتی در صورت بروز Exception یا Crashing برنامه، تمامی کانکشن‌های استخر به‌صورت کاملاً ایمن و منظم بسته می‌شوند.

## 🚦 ۷. متوقف‌سازی و آزادسازی نخ‌ها با `threading.Event` (مکانیزم Intercept)

* **چالش توقف بی‌ضرر (Non-busy Waiting):** در ابزارهای Intercept مانند Burp Suite، هنگامی که پکت شبکه دریافت می‌شود، اجرای نخ (Thread) سوکت کلاینت باید تا زمان تعیین تکلیف توسط کاربر (Forward یا Drop) متوقف بماند. استفاده از حلقه‌های شرطی مداوم (مثل `while True`) باعث درگیر شدن ۱۰۰ درصدی CPU (High CPU Usage) می‌شود.
* **استفاده از `threading.Event` و `event.wait()`:** با پیاده‌سازی مکانیزم ایونت در پایتون، نخ سوکت کلاینت بدون مصرف هیچ‌گونه منابع پردازشی CPU به حالت **Sleep / Block** می‌رود. به محض فراخوانی دستور `event.set()` توسط API دشبورد (پس از کلیک کاربر)، نخ جاری بلافاصله از حالت بلاک خارج شده و ادامه مسیر (ارسال یا قطع ارتباط) را طی می‌کند.
* **ایمنی در دسترسی هم‌زمان (Thread-Safety با Mutex):** از آنجا که چندین نخ کلاینت به‌صورت هم‌زمان ایونت‌های خود را در دیکشنری مشترک `intercept_events` ثبت یا حذف می‌کنند و API دشبورد نیز در نخی مجزا به آن دسترسی دارد، تمام عملیات‌های خواندن/نوشتن روی این دیکشنری تحت یک قفل متقابل (`threading.Lock()`) انجام می‌شود تا از وقوع **Race Condition** و خطاهای خطرساز تداخل حافظه جلوگیری گردد.
* **مدیریت زمان انقضا (Timeout Handling) و پاک‌سازی حافظه:**
  * تعیین مقدار تایم‌اوت (`timeout=300.0`) در `event.wait()` تضمین می‌کند در صورت عدم واکنش کاربر پس از ۵ دقیقه، نخ کلاینت برای همیشه معلق نمانده و به‌صورت پیش‌فرض (Fallback) پکت را Forward کند.
  * قرار دادن متد `pop` در بلوک `finally` تضمین می‌کند ایونت‌ها پس از تعیین تکلیف حتماً از حافظه RAM پاک شوند تا سیستم دچار **Memory Leak** نشود.

## 🔄 ۸. ارتباط بین‌پروسسی (IPC) و همگام‌سازی state از طریق Database Polling

* **چالش تداخل پروسس‌ها (Process Memory Boundary):** سرور پروکسی (`inspector_server.py`) و API دشبورد (`FastAPI`) در دو پروسس کاملاً مجزا با فضای حافظه (RAM) مستقل اجرا می‌شوند. بنابراین، اشیائی مانند `threading.Event()` که در RAM سرور ساخته می‌شوند، از داخل پروسس دشبورد قابل دسترسی نیستند و فراخوانی متد `.set()` روی آن‌ها کارساز نخواهد بود.
* **راهکار Database-backed Polling:** برای عبور از مرز حافظه پروسس‌ها، **پستگرس به عنوان رسانهٔ مشترک ارتباطی (IPC Channel)** انتخاب شد. تابع `wait_for_user_action` طوری بازنویسی شد که هر ۵۰۰ میلی‌ثانیه وضعیت ستون `status` را از جدول `intercept_queue` استعلام (Poll) کند.
* **دستاورد:** با این ساختار، هر برنامه‌ای (چه اسکریپت‌های تست، چه API دشبورد و چه ابزارهای CLI خارجی) می‌تواند با یک `UPDATE` ساده روی دیتابیس، وضعیت پکت را تغییر دهد و سرور پروکسی آنی از حالت Block خارج می‌شود.

---

## 🛑 ۹. پیاده‌سازی منطق Drop و قطع ارتباط امن کلاینت

* **عدم ارسال به مقصد (Interception Enforcement):** در صورتی که اکشن دریافتی برای یک `request_id` برابر با `dropped` باشد، سرور پروکسی موظف است پردازش را متوقف کرده و به هیچ عنوان اتصال سوکت سمت مقصد (`httpbin` یا هر تارگت دیگری) را برقرار نکند.
* **پاسخ بلاک صریح (403 Forbidden):** به‌جای رها کردن ناگهانی سوکت کلاینت (که باعث خطای `ECONNRESET` و گیج شدن کلاینت می‌شود)، یک پاسخ استاندارد `HTTP/1.1 403 Forbidden` همراه با بدنهٔ توضیحی برای کلاینت ارسال شده و سپس سوکت به‌صورت کاملاً پاکیزه بسته می‌شود.
* **تضمین عدم ایجاد Deadlock و Leaked Thread:** با بسته شدن سوکت کلاینت در بلوک `dropped` و اجرای قطعه‌کد پاک‌سازی در `finally`، تمام منابع تخصیص‌یافته به آن ترید (شامل اتصال دیتابیس و آی‌دی ایونت در حافظه) آزاد می‌شوند.

## 🏎️ ۱۰. مدیریت هم‌زمانی و یکپارچه‌سازی اجرای سرویس‌ها با Orchestrator Runner

* **چالش اجرای چندگانه (Multi-terminal Friction):** معماری پروژه از دو سرویس مجزا تشکیل شده است: سرور سوکت/پروکسی (`inspector_tools.server`) و رابط کاربری CLI (`dashboard.app`). اجرای دستی هر کدام در ترمینال‌های جداگانه باعث کاهش سرعت تست و پیچیدگی چرخه‌ی توسعه (Developer Experience) می‌شد.
* **استفاده از `subprocess.Popen` برای اجرای Background:** پروسس سرور پروکسی با ابزار `Popen` به صورت Non-blocking در پس‌زمینه سیستم‌عامل بالامی‌آید تا نخ اصلی اجرای اسکریپت رانر برای بالا آوردن رابط کاربری آزاد بماند.
* **تضمین تطابق محیط اجرا با `sys.executable`:** به‌جای فراخوانی مستقیم دستور `python` یا `python3` که ممکن است به مفسر جهانی (Global Python) اشاره کند، از `sys.executable` استفاده شد. این کار تضمین می‌کند که هر دو پروسس دقیقاً داخل همان محیط مجازی (Virtual Environment / venv) پروژه اجرا شوند و تمام وابستگی‌ها (Dependencies) به درستی بارگذاری گردند.
* **جلوگیری از ساخت Zombie Process با الگوی Cleanup در `finally`:**
  * در صورتی که دشبورد به هر دلیلی بسته‌شده یا با کلیدهای `Ctrl+C` متوقف شود، پروسس سرور پروکسی نباید در پس‌زمینه سیستم‌عامل به‌صورت معلق باقی بماند (باعث خطای `Address already in use` روی پورت سوکت در اجراهای بعدی می‌شود).
  * استفاده از ترکیب `server_process.terminate()` و `server_process.wait()` داخل بلوک `finally` تضمین می‌کند که با خروج از برنامه، سیگنال `SIGTERM` به سرور فرستاده شده و تمامی منابع اختصاص داده شده به آن به‌صورت کاملاً ایمن آزاد گردند.

# 📄 ADR: رفع مشکلات اجرای تعاملی پروژه در محیط Docker

**وضعیت:** پذیرفته‌شده (Accepted)
**تاریخ:** 1405/05/02

---

## 🎯 زمینه (Context)

پس از Dockerize کردن پروژه (v5.0.0)، با اجرای `docker compose up`، کانتینر `app` بدون هیچ خطای مشخصی خیلی سریع خارج می‌شد (`Exited (0)`) و سرویس پروکسی و داشبورد در دسترس نبودند. رفع این مشکل نیازمند چند مرحله عیب‌یابی مجزا بود که هرکدام یک لایه از مشکل را آشکار کردند.

---

## 🐛 مشکل ۱: عدم انتظار Runner برای Subprocess داشبورد

* **علت:** در `runner.py`، پروسس داشبورد با `subprocess.Popen` به‌صورت Non-blocking اجرا می‌شد، اما بلافاصله بدون فراخوانی `.wait()` وارد بلوک `finally` می‌شد. این باعث می‌شد بلافاصله پس از اجرای داشبورد، سیگنال `terminate()` به پروسس پروکسی ارسال شود.
* **راه‌حل:** افزودن `dashboard_process.wait()` بلافاصله پس از `Popen`، تا نخ اصلی رانر تا پایان واقعی اجرای داشبورد بلاک بماند.

## 🐛 مشکل ۲: عدم Expose شدن پورت سرویس در Docker Compose

* **علت:** در `docker-compose.yml`، بخش `ports` برای سرویس `app` تعریف نشده بود. پورت 8080 داخل کانتینر به‌درستی listen می‌کرد، اما از بیرون (هاست) قابل دسترس نبود.
* **تشخیص:** با اتصال از **داخل خود کانتینر** (`docker compose exec app python3 -c "socket.create_connection(...)"`) وضعیت سالم بودن سرور تأیید شد، در حالی که `curl` از هاست با خطای `Connection refused` مواجه می‌شد — نشانه‌ی قطعی نبود Port Mapping.
* **راه‌حل:** افزودن `ports: - "8080:8080"` به تعریف سرویس `app`.

## 🐛 مشکل ۳: اجرای Image قدیمی (Stale Image) پس از تغییر کد

* **علت:** `docker-compose.yml` تغییر کرده بود، اما Image به‌صورت خودکار Rebuild نشده بود. تغییرات کد جدید (fix مشکل ۱) هرگز وارد Image اجراشونده نمی‌شدند، در حالی که خطای ظاهری هنوز به مشکل قبلی شبیه بود.
* **تشخیص:** اجرای یک اسکریپت تست جدید با `docker compose run --rm app python debug_test.py` خطای `No such file or directory` داد — نشان‌دهنده این بود که فایل‌های جدید هاست اصلاً داخل Image کپی نشده‌اند، چون `COPY . .` در Dockerfile فقط زمان Build اجرا می‌شود.
* **راه‌حل:** اجرای صریح `docker compose build` (یا `--build`) پس از هر تغییر در کد یا Dockerfile، پیش از `up`/`run`.

## 🐛 مشکل ۴: `EOFError` روی `input()` به دلیل نبود TTY/STDIN

* **علت:** داشبورد CLI از تابع `input()` برای دریافت اکشن کاربر (`forward/drop/edit`) استفاده می‌کند. به‌صورت پیش‌فرض، کانتینرهای Docker به STDIN متصل نیستند و TTY تخصیص داده نمی‌شود؛ در نتیجه اولین فراخوانی `input()` بلافاصله با خطای `EOFError: EOF when reading a line` مواجه می‌شد.
* **قاعده‌ی کلی:** هر سرویسی که در داخل کانتینر به ورودی تعاملی از کاربر (`input()` یا معادل آن) نیاز دارد، باید هر دو گزینه‌ی زیر را در تعریف سرویس خود در `docker-compose.yml` فعال کند:
  ```yaml
  stdin_open: true   # معادل -i در docker run
  tty: true           # معادل -t در docker run
  ```
* **راه‌حل:** افزودن این دو خط به تعریف سرویس `app`.

## 🐛 مشکل ۵: تداخل STDIN هنگام Attach هم‌زمان چند سرویس

* **علت:** حتی پس از فعال‌سازی `stdin_open`/`tty`، اجرای `docker compose up` (که چند سرویس — `app` و `postgres` — را هم‌زمان Attach و لاگ‌هایشان را ترکیب می‌کند) باعث می‌شد ورودی تایپ‌شده در ترمینال به‌درستی به فرآیند `input()` داخل کانتینر `app` نرسد.
* **راه‌حل:** برای اجرای تعاملی، به‌جای `docker compose up`، سرویس‌های وابسته (مثل `postgres`) جدا و در پس‌زمینه بالا آورده می‌شوند و تنها سرویس تعاملی با `run` به‌صورت مستقل و تمیز به ترمینال متصل می‌شود:
  ```bash
  docker compose up -d postgres
  docker compose run --rm --service-ports app python runner.py
  ```

## ✅ نتیجه (Consequence)

## 🐛 ۱۱. باگ Content-Length نادرست هنگام Edit کردن Body درخواست

* **مشکل:** در تابع `rebuild_raw_http` (در `dashboard/app.py`)، هنگام بازسازی درخواست HTTP پس از ویرایش دستی توسط کاربر، هدرهای درخواست به‌طور کامل و بدون تغییر از نسخه‌ی اصلی کپی می‌شدند. این باعث می‌شد مقدار هدر `Content-Length` هم‌چنان برابر طول **Body قدیمی** باقی بماند، در حالی که Body واقعی که ارسال می‌شد طول متفاوتی (معمولاً بیشتر) داشت.
* **تشخیص:** با تست عملی روی `postman-echo.com/post` مشخص شد که وقتی Body یک درخواست POST از طریق حالت Edit تغییر می‌کند، سرور مقصد تنها به اندازه‌ی مقدار `Content-Length` قدیمی از بدنه‌ی جدید را می‌خواند و باقی محتوا **Truncate (بریده)** می‌شود. این باگ تنها زمانی قابل مشاهده بود که طول Body جدید با Body اصلی تفاوت داشت — به همین دلیل در تست‌های اولیه‌تر (که فقط Path و Host تغییر می‌کردند) دیده نشده بود.
* **راه‌حل:** پیش از بازسازی نهایی درخواست، هدر `Content-Length` قدیمی حذف و بر اساس طول واقعی Body جدید (به‌صورت بایت، با `len(body.encode("utf-8"))`) دوباره محاسبه و جایگزین می‌شود. محاسبه بر مبنای بایت (نه کاراکتر) انجام می‌شود تا برای محتوای غیر-ASCII هم نتیجه‌ی صحیح تضمین شود.
* **درس گرفته‌شده:** هر عملیات Edit روی HTTP Body که هدرهای اصلی را بازاستفاده می‌کند، باید هدرهای وابسته به طول محتوا (`Content-Length`) را صراحتاً بازمحاسبه کند؛ کپی کورکورانه‌ی هدرهای قدیمی در کنار محتوای جدید یک الگوی باگ‌زای رایج است.

## ⚠️ ۱۳. محدودیت شناخته‌شده: تداخل خروجی Thread ها با ورودی تعاملی در Dashboard CLI

* **مشاهده:** در تست همزمانی (Concurrency Test) با ارسال چند درخواست هم‌زمان، مشاهده شد که گاهی پیام `⚠️ Invalid choice!` نمایش داده می‌شود حتی زمانی که کاربر مقدار صحیحی (مانند `f`) وارد کرده است. کاربر مجبور به واردکردن مجدد مقدار می‌شود.
* **علت ریشه‌ای:** معماری فعلی Dashboard بر پایه‌ی CLI است، جایی که چندین Thread کلاینت به‌صورت هم‌زمان از طریق دستور `print()` روی همان ترمینال مشترک خروجی می‌نویسند، درحالی‌که تنها یک جریان ورودی (`input()`) برای دریافت تصمیم کاربر وجود دارد. زمانی که خروجی یک Thread پس‌زمینه (مثلاً لاگ اتصال کلاینت جدید) هم‌زمان با تایپ کاربر چاپ شود، ممکن است با کاراکتر ورودی کاربر ترکیب شده و رشته‌ی نامعتبری به `input()` تحویل داده شود.
* **بررسی صحت داده:** این محدودیت تنها مربوط به لایه‌ی نمایش/ورودی ترمینال است؛ منطق اصلی صف Intercept (تطابق `request_id` با محتوای صحیح آن، عدم قاطی‌شدن درخواست‌های هم‌زمان) در تست عملی صحیح و سالم عمل کرد.
* **تصمیم:** با توجه به این‌که این مشکل ذاتی معماری I/O ترمینال است (نه یک باگ منطقی در پردازش درخواست‌ها) و طبق نقشه‌ی راه پروژه، Dashboard در نسخه‌های بعدی (v6+) به یک رابط وب‌محور مبتنی بر FastAPI مهاجرت خواهد کرد، تصمیم گرفته شد این مورد به‌عنوان یک **محدودیت شناخته‌شده (Known Limitation)** مستند شود نه یک باگ فوری برای رفع.
* **چرا FastAPI این مشکل را ریشه‌ای حل می‌کند:** در معماری وب‌محور، هر تصمیم کاربر (Forward/Drop/Edit) از طریق یک HTTP Request مستقل (مثلاً یک `POST`) ارسال می‌شود، نه از طریق یک جریان ورودی مشترک با سایر Threadها. بنابراین رقابت بین چاپ لاگ و دریافت ورودی که در ترمینال مشترک رخ می‌دهد، در این معماری اصلاً موضوعیت نخواهد داشت.

## 🔄 ۱۵. شفاف‌سازی چالش معماری: Threading در برابر Async/Await

* **ریشهٔ گیجی در توسعه:** در نگاه اول، الگوی هم‌زمانی `asyncio` بسیار مدرن و سریع به‌نظر می‌رسد و این وسوسه ایجاد می‌شود که تمام بخش‌های پروکسی و دیتابیس به `async/await` تبدیل شوند. اما ترکیب ناآگاهانهٔ کد Synchronous و Asynchronous باعث بروز باگ‌های پیچیده و قفل شدن برنامه می‌شود.
* **تفاوت ساختاری در I/O Bound:**
  * **Threading (مدل فعلی پروکسی):** هر کلاینت یک نخ (Thread) مجزا دارد. زمان انتظار برای شبکه یا دیتابیس، صرفاً همان نخ را به حالت Block می‌برد و نیازی به کلمات کلیدی `async` و `await` ندارد.
  * **Asyncio (مدل FastAPI / Event Loop):** تمام درخواست‌ها روی یک Thread اصلی اجرا می‌شوند. اگر یک تابع غیر-Async (مانند کوئری دیتابیس معمولی) در این جریان اجرا شود، کل Event Loop برنامه‌ قفل شده و پاسخ‌دهی به سایر کلاینت‌ها متوقف می‌شود.
* **تصمیم معماری (Architectural Boundary):**
  * بخش **Socket Inspector** بر پایهٔ `threading` نگهداری می‌شود تا سادگی کدهای شبکه حفظ گردد و تعامل با دیتابیس از طریق `ConnectionPool` معمولی در `db_manager.py` صورت پذیرد[cite: 2].
  * در صورت نیاز به استفاده از `async def` در **FastAPI Dashboard**، از نسخهٔ Async درگاه دیتابیس (`AsyncConnectionPool`) استفاده خواهد شد تا مرز میان دنیای Synchronous پروکسی و Asynchronous دشبورد کاملاً شفاف و مجزا بماند.
